# Release identity must remain consistent

At release completion, the **reviewed pin, signed desired state, promoted image
and running production artifact** must identify the same release. Source HEAD
may be a successor with proven identical build inputs. Keep the image's actual
build revision; never relabel an older artifact as a new HEAD.

- Do not hand-edit pins. The authorized writer is
  `scripts/converge-yueboard-release-pin.py --from-head --deployed-board-revision <production-board> --deployed-node-revision <production-fleet>`.
  It updates the copies atomically and derives the schema floor from
  `git show <rev>:schema-floor.txt`; the floor is not an input.
- The two `--deployed-*` revisions validate ancestry only: deployed Board must
  precede the candidate, and deployed Node must precede the sidecar candidate.
  They are no longer recorded in files. The Release-A predecessor/target contract
  was removed on 2026-09-14. Incorrect inputs are rejected; omitting them performs
  pin convergence only.
- Since 2026-09-24 (P2 section 4 A3), convergence writes only the two yueto-ci
  files: the contract and central policy test. It does not write YueOps; those
  three former projections caused a Board-to-Ops release cycle. Commit yueto-ci
  after convergence; promotion reads that reviewed state.
- Do not hand-edit `release.yaml`. `ship.sh` writes it and `release-yaml.py seal`
  signs it. YueOps deployers, rollouts and migrators consume only verified signed
  state. Deliberate rollback uses `release-yaml.py write --rollback` then `seal`;
  late older candidates cannot overwrite newer desired state.
- The 2026-09-24 build-input rule replaced the old rule allowing only
  `.gitleaksignore` to lead the pin. Use the existing fingerprints in
  `scripts/release-state.py --fleet --inputs` to establish equality for every
  input. Unreadable or unproven inputs are UNKNOWN; calling a change documentation
  or tests is not an exemption.
- `schema-compat.txt` records the production floor only after successful actual
  deployment. Tests still read it, but it has been excluded from Board image
  inputs since 2026-09-30. Advancing it alone does not move the reviewed pin,
  rebuild an image or relabel production. `schema-floor.txt` and migration SQL
  remain build inputs and require a reviewed release when changed.
- For a new candidate, converge the reviewed pin first, then run
  `release-yaml.py source-check` for ancestry and floor. Do not declare release
  consistency before promotion and production readback.

Use `release-chain` for constraints, `docs/release-chain-runbook.md` for commands,

# Release chain (Yue.to)

The authoritative commands are in `docs/release-chain-runbook.md`, calibrated
through a real run on 2026-08-24. This skill records constraints needed during
planning, before copying commands.

## Start by establishing current state

For a readback-only task, use evidence-discipline's
[read-only checklist](../evidence-discipline/references/readonly-operations.md#1-post-release-readback).
That task does not authorize the release operations described below.

```bash
scripts/release-state.py            # HEAD / reviewed pin / promoted artifact / running production.
scripts/release-state.py --fleet -v # Actual revisions across direct hosts; detects split fleets.
scripts/release-state.py --packages # Tuning .deb inventory, which image digest/pin checks cannot see.
```

Unreachable rows are **UNKNOWN, never OK**. Identify them before any claim that
all hosts run the target version.

Run local YueLink commands and Git tag pushes through
`scripts/with-release-sdk.sh <command> [arguments...]`. It reuses release SDK
verification and sets PATH/FLUTTER_ROOT for Flutter, Dart and Git hooks. Gauntlet
selects the same SDK, but its child environment cannot propagate back to the
calling shell. Passing gauntlet does not validate a later bare git push's SDK.

```

```

### `release.yaml` is the sole deployment expectation; ship.sh writes it

Root `release.yaml` separates promoted `components` history from approved
`desired` state. After promotion and signature/SBOM/provenance verification,
`scripts/ship.sh` writes, seals with a detached GPG signature
`release.yaml.asc`, signs the commit, pushes, and projects to bastion
`/var/lib/yueops/fleet-reconcile/release.yaml(+.asc)` and panel
`/root/release.yaml(+.asc)`. The seal uses the same signing subkey as commits.
release-state's pin column reads desired. **Never hand-edit without the native
write/seal chain**; readers reject unsealed changes.

Since P2 §4 A3 (2026-09-24), Ops deployers, the one-phase panel deployer, schema
migrator, fleet rollout (signed roots and weekly runtime bundles), Docker
ceremony, fleet-reconcile and the web container read only verified
`desired.production`. Missing/bad signatures, generation rollback or unwritable
generation state fail closed; there is no projection fallback.
`yueops/scripts/yue-node.image(.revision)`, `yueboard.image` and
`yueboard-schema-release.env` were removed. ship.sh no longer writes image pins
back into Ops. `SHIP_WRITE_YUEOPS_PROJECTIONS=1` is only for a coordinated A3
rollback including the matching Ops rollback, not ordinary delivery.

If sealing fails, ship stops after promotion/write. Repair GPG, run
`release-yaml.py seal`, commit, then resume with `--from-promoted`.

P2 #11 records desired generation at startup and writes with
`--expect-generation`. New revisions must be descendants of or equal to current
desired; older, forked or unprovable candidates fail. Intentional rollback uses
`scripts/release-yaml.py write --component <c> --revision <old-rev> --digest <old-digest> --rollback`,
then seal and projection, targeting an already promoted GHCR image.

B1 permits Ops' three desired images to span revisions only when older members
are ancestors of the newest and their image-input fingerprints are identical.
The deployer recomputes this, including provenance-verified recipes. See
`docs/2026-09-24-p2-p4-release-decoupling-design.md` §9–§10.

## A push to Board is not merely local

Desired, Board HEAD, promoted image and running panel must reconcile under the
release rules. Since P2 #11 (2026-09-24), promotion accepts a candidate that is
on the default branch (HEAD or ancestor), has image inputs identical to HEAD,
and is no older than latest. `yueto-ci/scripts/promote-source-gate.py` repeats
checks immediately before moving tags. Input-neutral pushes do not invalidate
promotion; changed image inputs do. The exact reviewed-pin requirement remains.

A Board push requires checking the existing release identities and effective
image inputs. When the actual comparator proves a clean default-branch successor
has unchanged inputs and the same schema floor, retain the reviewed pin and the
actual promoted/running image revision. A documentation or schema-compat-only
successor does not itself require a rebuild or ship under those conditions.
Names such as documentation or tests are not exemptions: COPY and ignore rules
determine inputs, and UNKNOWN must refuse. Changed inputs require normal reviewed
pin convergence (only yueto-ci), the signed release chain and production readback.
Never relabel the older image as the new HEAD. Use the existing fingerprint
consumer and identity rules in `.claude/rules/release-pins.md`.

## One-phase panel deployment through ship.sh

Since 2026-09-15, the former mint/converge/deploy three-phase procedure and its
per-Ops-revision sealed deadman are no longer the ordinary path. Real runs on
09-15 and 09-20 verified the replacement.

```bash
scripts/ship.sh yueboard --foreground    # Build → promote → verify → project → deploy.
scripts/ship.sh yueboard --from-promoted --foreground # Resume after promotion; no duplicate build.
scripts/ship.sh --auto --foreground      # Select work using release-state.
scripts/ship.sh <svc> --detach           # Durable local logs under ~/.yueto-ship-logs/.
```

Non-TTY and recognized agent calls detach by default. Sequential release steps
must use `--foreground` or wait for the printed `<log>.run.json` to contain a
numeric `exit_code` of zero. Startup acknowledgment is not release success;
null, missing or unreadable final status cannot authorize a dependent step.

`ship.sh yue-node --foreground` builds, promotes, verifies and projects signed desired only;
it **does not roll the fleet**. Actual rollout runs
`rollout-yue-node-image.sh` from a signed Ops release root and requires slot
readback. Published images do not prove installed nodes.

ship.sh projects ten explicit dependencies to the panel, which cannot reach
GitHub: six deployment scripts, a public env template, a verification keyring,
release.yaml and its signature. It then runs `panel-deploy.sh <digest>`:
signature + two SBOMs + provenance; exact desired digest; the candidate image's
own migrate status with no Pending; atomic env update from image labels;
container start; two consecutive readyz checks; retain the stopped predecessor
for rollback; remove older rollback containers. Pending migrations refuse
deployment and point to `run-yueboard-schema-migration.sh --apply`.

The panel's `/opt/yueops` is a **detached, remote-less projection directory**.
On 2026-09-20 its HEAD still had schema floor 43 while projected files contained
09-14 scripts and status showed many M/D paths. Never git pull there or judge
installed bytes by git log. Use actual file bytes/mtime and ship projection
receipts. Connect through the bastion; the recorded panel address was
`ssh root@66.55.76.208`, not a locally reachable key path.

## Promotion criteria observed in practice

- Take digests **only from promotion-step logs**, never build-step logs.
- Promotion is not atomic across services. Ops' three independent jobs can leave
  partial promotion (two latest tags moved, one did not). Deployment validates
  signed desired per image. Same-revision images or B1-proven ancestor/input-
  equivalent members are permitted; partial promotion is not full deployment.
- Freeze relevant source during promotion for both Ops and Board.
- ship's run-association queue window is up to 100 minutes (`queue_cap`, raised
  from 45 on 2026-10-11). A same-revision poll-sources build ahead of it can spend
  40–50 minutes validating Ops. Long queued state is not a reason to restart.
  Absence of any new matching run within 180 seconds is a distinct failure.
- Concurrent ship writes use a generation gate; rejection of the later writer
  is correct. If promotion and verification already succeeded, resume with
  `scripts/ship.sh <svc> --from-promoted --foreground`. Locks are session-scoped; deliberately
  concurrent releases first acquire their complete repository set with
  `release-lock.py acquire --repos <all-repositories>` (three parallel runs were
  measured on 2026-10-11).

For combined entry, ACL and host-executor changes, drain work as specified in

## Fleet rollout pitfalls

### A. `/opt/yueops` is not a signed release root

Its operational .env/data/pycache and other ignored files make pristine-root
assertions structurally impossible. Mint a clean root:

```sh
ssh bastion 'cd /opt/yueops && ROOT=$(bash scripts/make-release-root.sh)'
```

### B. Detach the fleet rollout

An SSH-bound driver dies with the session, leaving
`transaction=prepared-for-soak` and lost stdout. Restarting then encounters
`a durable Yue-Node transaction is already active`. Use the native detached
path (`setsid nohup … & disown` on the remote Linux host). Authoritative logs
are always in `/var/log/yueops-rollout/`, not inferred from stdout. After manual
finalization, wait the full 240-second lease before another rollout.

**Concurrency defaults to 4; higher values lack evidence.** Earlier skill text
said ≤3, but Ops `3161d06` had moved the default from 2 to 4. A stale literal
assertion `CONCURRENCY=${CONCURRENCY:-2}` failed the batch; the test now guards
the supported 1..4 interval in
`yueops/tests/test_yue_node_host_convergence.py`.

Evidence for 4: `/var/log/yueops-rollout/20260831-214836.log`,
21:48:49→22:19:26, 30.6 minutes for 20 hosts, ok=20 fail=0 unreachable=1;
no `RETRY|throttl|Connection refused|Too many|max startups` matches and zero
accounting-drain FATAL. The same night's concurrency=2 comparison took roughly
81 minutes for 27 hosts, about 3 minutes/host versus 1.5 at 4. This is one real
data point, **not a load study**. No separate control-plane or billing-queue
pressure curve was collected; measure both before increasing concurrency.

### Editing rollout scripts

- `readonly` inside rollout_one is not function-local. The second host can fail
  with readonly variable and leave prepared transactions although the first
  canary passed. Put constants at top level. Guard:
  `tests/test_rollout_per_host_scope_20260830.py`.
- Transport failure is not mutation failure. Both yue-sg slots had been rebuilt,
  healthy and RUNTIME_PREPARED when commit SSH timed out with 255, blocking the
  remaining 17 hosts. `finalize_remote_transaction` retries **only SSH's 255**,
  3×15s. Return finalizer verdicts unchanged; retrying a verdict can disguise a
  real defect as an intermittent event.

An interrupted rollout leaves prepared transactions. The host
`yue-node-rollout-recovery.timer` has been observed to finalize them. If manual
finalization is necessary, use the verified SHA256 of
`finalize-yue-node-rollout-runtime.sh` with `--action commit`, then wait the
full 240-second lease before retrying.

## Validation when private Actions are frozen

Determine actual execution from job steps and annotations each time. Historical
zero-step runs are not permanent state. Public yueto-ci poll-sources is scheduled
every 20 minutes to compare source HEAD with built-<sha>; actual scheduling can
lag, so 20 minutes is not an SLA. `validate-<repo>` performs product tests, but
cannot replace uncovered scans or workspace contracts. Local gauntlet remains
the real gate: missing tools/repos are SKIP, never PASS, and insufficient executed
stages fail. Only the account owner can resolve billing/spending-limit freezes.

## Closeout criteria

```bash
scripts/release-state.py --fleet -v   # Reconcile all released components; distinguish unrelated pending work.
scripts/check-all-contracts.sh        # Full current set; --list supplies its size.
ssh bastion 'systemctl --failed'      # Also inspect oneshot Result values individually.
```

A complete three-component server release requires all three server rows OK.
Recheck nodes after **every Board deployment or rollback**; brief 502s can be
fatal to an already backlogged outbox. A partial-component release must not be

## Other release gates

- YueLink: version triplet + final signed source → push → exact source-attestation
  → private signed stable tag → public release.sh → five-platform build →
  automatic signed promotion + R2. There is no prerelease build channel; a
  successful build goes stable. Complete gates before building. Public tags are
  immutable; a change requires a version bump. Promotion's ed25519 private key
  is not on the workstation; emergency manual promotion runs only on bastion
  through the runbook.
- Measure feature-flag timing. Current `FeatureFlags` fetches at startup, not
  instantaneous circuit breaking for active sessions. Until refresh is delivered,
  receipts can claim only startup/next-fetch effect.
- Board requires the fixed GPG release signer. Disabling commit signing blocks
  the release gate.
- `yuelink-ci` is generated: after changing YueLink build.yml, run
  `./sync-build.sh ../yuelink` in the mirror repository.

## Panel deployment and fleet rollout must not overlap

On 2026-08-29, a panel rebuild caused reconnects and 94 distinct
node_presence_streams instance IDs in the following minute, compared with 2
before. `nodeProcessFenceAfter` is 4 minutes; old/new presence coexist,
(server,machine) leases are not exclusive and accounting queues block. The
rollout's 30-second drain gate then failed with prepare_exit=43.

Serialize them. After panel deployment, wait at least 5 minutes before fleet
rollout; do not deploy the panel during rollout. A single-host stop/start has
the same fence: repeated immediate retries create new conflicts. Prove outbox
drain before stopping a container under the applicable storage/transaction rules;
after failure, allow 5 minutes before a clean retry. Docker StartedAt is UTC.
See runbook §3.6 / §3.7.

## Finish pushes before building

Images bake their source revision and deployment validates exact identity.
On 2026-08-29, building before pin convergence failed five builds; building before
pushing Node pins produced three undeployable images.

Sequence: commit/push source → converge/push yueto-ci → build/promote with inputs
frozen → take promotion digest → verify → write/seal/project release.yaml →
deploy. A3 removed the intervening Ops image-pin commit.

Since P2 #11, only pushes changing this image's build inputs invalidate promotion.
Since P3, `poll-skip-decision.py` skips builds whose input-equivalent promoted
image has verified provenance; unknown means build. A HEAD without built-<sha>
can therefore be legitimate. ship.sh's explicit promotion builds are unaffected.
See runbook §3.5b.

## Build triggers and manual promotion

`yueto-ci/poll-sources.yml` pulls source HEADs on a 20-minute schedule and compares
GHCR built-<short sha> tags. It **builds only, never promotes**. The former private
repository_dispatch path required `YUETO_CI_DISPATCH_PAT`, absent from all three
repositories: 428 runs across Board/Node/Ops, zero success. Persistent red hid a
broken frontend gate and a pytest suite dead for two days. Pulling reuses existing
`YUETO_CI_PAT`, without a new credential.

Moving `:sha-*` / `:latest` remains deliberate:

```bash
gh workflow run build.yml -R onesyue/yueto-ci -f service=<svc> -f ref=<40-hex> -f promote=true
```

Ops, including a single image or all, additionally requires
`-f migration_base=<40-hex-previous-release>`. ship.sh reads the verified prior
root desired and supplies it. Public gates verify existence/ancestry and lint
SQL across the entire range, not a guessed HEAD^ boundary. Polling uses the
promoted revision with verified master provenance. If the baseline cannot be
proved, fail rather than dispatching an empty range as success.
`scripts/kick-builds.sh` dispatches poll-sources immediately instead of waiting
for scheduling. GitHub throttles that cron to roughly one run per 2–5 h
(measured 2026-09-14), so do not wait on the 20-minute schedule.

### Central CI is part of the supply-chain trust boundary

`yueops/scripts/verify-image-signature.sh` anchors cosign certificate identity to

The 2026-09-27 tightening accepted only master: all 223 historical ledger digests
had promotion runs from master; main is no longer accepted. SLSA provenance

## Cross-repo coupling that isn't visible in any single repo

Board schema migration is decoupled from fleet identity (§III.2). Its constraints
are expand/contract backward compatibility and clean migrate status, independent
of fleet revision. An unreachable host no longer creates the former circular
panel-release prerequisite; zero DEFER is not a prerequisite either.

Do not restore fault baseline, canonical evidence, `CROSSING_PREDECESSOR_*`,
`CROSSING_TARGET_NODE_REVISION`, `--adopt-proved-identity` or
`--required-node-revision`. `rollout-yueops-agent.sh` remains, but its old
baseline gate does not.

### `release.yaml` is the sole deployment expectation; ship.sh writes it

Root `release.yaml` separates promoted `components` history from approved
`desired` state. After promotion and signature/SBOM/provenance verification,
`scripts/ship.sh` writes, seals with a detached GPG signature
`release.yaml.asc`, signs the commit, pushes, and projects to bastion
`/var/lib/yueops/fleet-reconcile/release.yaml(+.asc)` and panel
`/root/release.yaml(+.asc)`. The seal uses the same signing subkey as commits.
release-state's pin column reads desired. **Never hand-edit without the native
write/seal chain**; readers reject unsealed changes.

Since P2 §4 A3 (2026-09-24), Ops deployers, the one-phase panel deployer, schema
migrator, fleet rollout (signed roots and weekly runtime bundles), Docker
ceremony, fleet-reconcile and the web container read only verified
`desired.production`. Missing/bad signatures, generation rollback or unwritable
generation state fail closed; there is no projection fallback.
`yueops/scripts/yue-node.image(.revision)`, `yueboard.image` and
`yueboard-schema-release.env` were removed. ship.sh no longer writes image pins
back into Ops. `SHIP_WRITE_YUEOPS_PROJECTIONS=1` is only for a coordinated A3
rollback including the matching Ops rollback, not ordinary delivery.

If sealing fails, ship stops after promotion/write. Repair GPG, run
`release-yaml.py seal`, commit, then resume with `--from-promoted`.

P2 #11 records desired generation at startup and writes with
`--expect-generation`. New revisions must be descendants of or equal to current
desired; older, forked or unprovable candidates fail. Intentional rollback uses
`scripts/release-yaml.py write --component <c> --revision <old-rev> --digest <old-digest> --rollback`,
then seal and projection, targeting an already promoted GHCR image.

B1 permits Ops' three desired images to span revisions only when older members
are ancestors of the newest and their image-input fingerprints are identical.
The deployer recomputes this, including provenance-verified recipes. See
`docs/2026-09-24-p2-p4-release-decoupling-design.md` §9–§10.

## A push to Board is not merely local

Desired, Board HEAD, promoted image and running panel must reconcile under the
release rules. Since P2 #11 (2026-09-24), promotion accepts a candidate that is
on the default branch (HEAD or ancestor), has image inputs identical to HEAD,
and is no older than latest. `yueto-ci/scripts/promote-source-gate.py` repeats
checks immediately before moving tags. Input-neutral pushes do not invalidate
promotion; changed image inputs do. The exact reviewed-pin requirement remains.

A Board push requires checking the existing release identities and effective
image inputs. When the actual comparator proves a clean default-branch successor
has unchanged inputs and the same schema floor, retain the reviewed pin and the
actual promoted/running image revision. A documentation or schema-compat-only
successor does not itself require a rebuild or ship under those conditions.
Names such as documentation or tests are not exemptions: COPY and ignore rules
determine inputs, and UNKNOWN must refuse. Changed inputs require normal reviewed
pin convergence (only yueto-ci), the signed release chain and production readback.
Never relabel the older image as the new HEAD. Use the existing fingerprint
consumer and identity rules in `.claude/rules/release-pins.md`.

## One-phase panel deployment through ship.sh

Since 2026-09-15, the former mint/converge/deploy three-phase procedure and its
per-Ops-revision sealed deadman are no longer the ordinary path. Real runs on
09-15 and 09-20 verified the replacement.

```bash
scripts/ship.sh yueboard --foreground    # Build → promote → verify → project → deploy.
scripts/ship.sh yueboard --from-promoted --foreground # Resume after promotion; no duplicate build.
scripts/ship.sh --auto --foreground      # Select work using release-state.
scripts/ship.sh <svc> --detach           # Durable local logs under ~/.yueto-ship-logs/.
```

Non-TTY and recognized agent calls detach by default. Sequential release steps
must use `--foreground` or wait for the printed `<log>.run.json` to contain a
numeric `exit_code` of zero. Startup acknowledgment is not release success;
null, missing or unreadable final status cannot authorize a dependent step.

`ship.sh yue-node --foreground` builds, promotes, verifies and projects signed desired only;
it **does not roll the fleet**. Actual rollout runs
`rollout-yue-node-image.sh` from a signed Ops release root and requires slot
readback. Published images do not prove installed nodes.

ship.sh projects ten explicit dependencies to the panel, which cannot reach
GitHub: six deployment scripts, a public env template, a verification keyring,
release.yaml and its signature. It then runs `panel-deploy.sh <digest>`:
signature + two SBOMs + provenance; exact desired digest; the candidate image's
own migrate status with no Pending; atomic env update from image labels;
container start; two consecutive readyz checks; retain the stopped predecessor
for rollback; remove older rollback containers. Pending migrations refuse
deployment and point to `run-yueboard-schema-migration.sh --apply`.

The panel's `/opt/yueops` is a **detached, remote-less projection directory**.
On 2026-09-20 its HEAD still had schema floor 43 while projected files contained
09-14 scripts and status showed many M/D paths. Never git pull there or judge
installed bytes by git log. Use actual file bytes/mtime and ship projection
receipts. Connect through the bastion; the recorded panel address was
`ssh root@66.55.76.208`, not a locally reachable key path.

## Promotion criteria observed in practice

- Take digests **only from promotion-step logs**, never build-step logs.
- Promotion is not atomic across services. Ops' three independent jobs can leave
  partial promotion (two latest tags moved, one did not). Deployment validates
  signed desired per image. Same-revision images or B1-proven ancestor/input-
  equivalent members are permitted; partial promotion is not full deployment.
- Freeze relevant source during promotion for both Ops and Board.
- ship's run-association queue window is up to 100 minutes (`queue_cap`, raised
  from 45 on 2026-10-11). A same-revision poll-sources build ahead of it can spend
  40–50 minutes validating Ops. Long queued state is not a reason to restart.
  Absence of any new matching run within 180 seconds is a distinct failure.
- Concurrent ship writes use a generation gate; rejection of the later writer
  is correct. If promotion and verification already succeeded, resume with
  `scripts/ship.sh <svc> --from-promoted --foreground`. Locks are session-scoped; deliberately
  concurrent releases first acquire their complete repository set with
  `release-lock.py acquire --repos <all-repositories>` (three parallel runs were
  measured on 2026-10-11).

## Fleet rollout pitfalls

### A. `/opt/yueops` is not a signed release root

Its operational .env/data/pycache and other ignored files make pristine-root
assertions structurally impossible. Mint a clean root:

```sh
ssh bastion 'cd /opt/yueops && ROOT=$(bash scripts/make-release-root.sh)'
```

### B. Detach the fleet rollout

An SSH-bound driver dies with the session, leaving
`transaction=prepared-for-soak` and lost stdout. Restarting then encounters
`a durable Yue-Node transaction is already active`. Use the native detached
path (`setsid nohup … & disown` on the remote Linux host). Authoritative logs
are always in `/var/log/yueops-rollout/`, not inferred from stdout. After manual
finalization, wait the full 240-second lease before another rollout.

**Concurrency defaults to 4; higher values lack evidence.** Earlier skill text
said ≤3, but Ops `3161d06` had moved the default from 2 to 4. A stale literal
assertion `CONCURRENCY=${CONCURRENCY:-2}` failed the batch; the test now guards
the supported 1..4 interval in
`yueops/tests/test_yue_node_host_convergence.py`.

Evidence for 4: `/var/log/yueops-rollout/20260831-214836.log`,
21:48:49→22:19:26, 30.6 minutes for 20 hosts, ok=20 fail=0 unreachable=1;
no `RETRY|throttl|Connection refused|Too many|max startups` matches and zero
accounting-drain FATAL. The same night's concurrency=2 comparison took roughly
81 minutes for 27 hosts, about 3 minutes/host versus 1.5 at 4. This is one real
data point, **not a load study**. No separate control-plane or billing-queue
pressure curve was collected; measure both before increasing concurrency.

### Editing rollout scripts

- `readonly` inside rollout_one is not function-local. The second host can fail
  with readonly variable and leave prepared transactions although the first
  canary passed. Put constants at top level. Guard:
  `tests/test_rollout_per_host_scope_20260830.py`.
- Transport failure is not mutation failure. Both yue-sg slots had been rebuilt,
  healthy and RUNTIME_PREPARED when commit SSH timed out with 255, blocking the
  remaining 17 hosts. `finalize_remote_transaction` retries **only SSH's 255**,
  3×15s. Return finalizer verdicts unchanged; retrying a verdict can disguise a
  real defect as an intermittent event.

An interrupted rollout leaves prepared transactions. The host
`yue-node-rollout-recovery.timer` has been observed to finalize them. If manual
finalization is necessary, use the verified SHA256 of
`finalize-yue-node-rollout-runtime.sh` with `--action commit`, then wait the
full 240-second lease before retrying.

- YueLink: version triplet + final signed source → push → exact source-attestation

  immutable; a change requires a version bump. Promotion's ed25519 private key

- `yuelink-ci` is generated: after changing YueLink build.yml, run

## Panel deployment and fleet rollout must not overlap

On 2026-08-29, a panel rebuild caused reconnects and 94 distinct
node_presence_streams instance IDs in the following minute, compared with 2
before. `nodeProcessFenceAfter` is 4 minutes; old/new presence coexist,
(server,machine) leases are not exclusive and accounting queues block. The
rollout's 30-second drain gate then failed with prepare_exit=43.

Serialize them. After panel deployment, wait at least 5 minutes before fleet
rollout; do not deploy the panel during rollout. A single-host stop/start has
the same fence: repeated immediate retries create new conflicts. Prove outbox
drain before stopping a container under the applicable storage/transaction rules;
after failure, allow 5 minutes before a clean retry. Docker StartedAt is UTC.
See runbook §3.6 / §3.7.

## Finish pushes before building

Images bake their source revision and deployment validates exact identity.

pushing Node pins produced three undeployable images.

Sequence: commit/push source → converge/push yueto-ci → build/promote with inputs
frozen → take promotion digest → verify → write/seal/project release.yaml →

# Release identity must remain consistent

At release completion, the **reviewed pin, signed desired state, promoted image
and running production artifact** must identify the same release. Source HEAD
may be a successor with proven identical build inputs. Keep the image's actual
build revision; never relabel an older artifact as a new HEAD.

- Do not hand-edit pins. The authorized writer is
  `scripts/converge-yueboard-release-pin.py --from-head --deployed-board-revision <production-board> --deployed-node-revision <production-fleet>`.
  It updates the copies atomically and derives the schema floor from
  `git show <rev>:schema-floor.txt`; the floor is not an input.
- The two `--deployed-*` revisions validate ancestry only: deployed Board must
  precede the candidate, and deployed Node must precede the sidecar candidate.
  They are no longer recorded in files. The Release-A predecessor/target contract
  was removed on 2026-09-14. Incorrect inputs are rejected; omitting them performs
  pin convergence only.
- Since 2026-09-24 (P2 section 4 A3), convergence writes only the two yueto-ci
  files: the contract and central policy test. It does not write YueOps; those
  three former projections caused a Board-to-Ops release cycle. Commit yueto-ci
  after convergence; promotion reads that reviewed state.
- Do not hand-edit `release.yaml`. `ship.sh` writes it and `release-yaml.py seal`
  signs it. YueOps deployers, rollouts and migrators consume only verified signed
  state. Deliberate rollback uses `release-yaml.py write --rollback` then `seal`;
  late older candidates cannot overwrite newer desired state.
- The 2026-09-24 build-input rule replaced the old rule allowing only
  `.gitleaksignore` to lead the pin. Use the existing fingerprints in
  `scripts/release-state.py --fleet --inputs` to establish equality for every
  input. Unreadable or unproven inputs are UNKNOWN; calling a change documentation
  or tests is not an exemption.
- `schema-compat.txt` records the production floor only after successful actual
  deployment. Tests still read it, but it has been excluded from Board image
  inputs since 2026-09-30. Advancing it alone does not move the reviewed pin,
  rebuild an image or relabel production. `schema-floor.txt` and migration SQL

def _unquote(value: str) -> str:
    value = value.strip()
    if len(value) >= 2 and value[0] == value[-1] and value[0] in ('"', "'"):
        return value[1:-1]
    return value


def parse(text: str) -> dict:
    """把扁平子集 YAML 解析成嵌套 dict（所有标量都是 str）。

    只接受：2 空格缩进、`key:`（开映射）与 `key: value`、以 # 起头的整行注释、空行。
    任何别的东西都报错并带行号——release.yaml 是机器写的，形状之外的内容就是手改。
    """
    root: dict = {}
    stack: list[tuple[int, dict]] = [(-1, root)]
    for lineno, raw in enumerate(text.splitlines(), 1):
        if not raw.strip() or raw.lstrip().startswith("#"):
            continue
        indent = len(raw) - len(raw.lstrip(" "))
        if indent % 2:
            raise ReleaseYamlError(f"第 {lineno} 行缩进不是 2 的倍数")
        line = raw.strip()
        if ":" not in line:
            raise ReleaseYamlError(f"第 {lineno} 行不是 key: value 形式：{line!r}")
        key, _, value = line.partition(":")
        key = key.strip()
        if not KEY_RE.match(key):
            raise ReleaseYamlError(f"第 {lineno} 行的键不合法：{key!r}")
        while stack and stack[-1][0] >= indent:
            stack.pop()
        if not stack:
            raise ReleaseYamlError(f"第 {lineno} 行缩进回退过头")
        parent_indent, parent = stack[-1]
        if indent != parent_indent + 2 and not (parent is root and indent == 0):
            raise ReleaseYamlError(f"第 {lineno} 行缩进 {indent} 与上层 {parent_indent} 不衔接")
        if key in parent:
            raise ReleaseYamlError(f"第 {lineno} 行重复的键：{key!r}")
        if value.strip() == "":
            child: dict = {}
            parent[key] = child
            stack.append((indent, child))
        else:
            if value.strip().startswith("#"):
                raise ReleaseYamlError(f"第 {lineno} 行的值为空（只有注释）")
            parent[key] = _unquote(value.split(" #", 1)[0])
    return root


def _emit_scalar(value: str) -> str:
    # 时间戳带冒号与 T/Z，真 YAML 解析器会把它变成 datetime；统一加引号，
    # 让 PyYAML 与本解析器读出同一个字符串。
    if TS_RE.match(value) or ":" in value or value.strip() != value or value == "":
        return json.dumps(value)
    return value


def emit(record: dict) -> str:
    out = [HEADER.rstrip("\n"), f"schema: {record.get('schema', SCHEMA)}", "components:"]
    comps = record.get("components", {})
    for name in COMPONENTS:
        if name not in comps:
            continue
        out.append(f"  {name}:")
        for field in FIELDS:
            out.append(f"    {field}: {_emit_scalar(str(comps[name][field]))}")
    desired = record.get("desired")
    if desired:
        out.append("desired:")
        out.append(f"  generation: {desired['generation']}")
        out.append("  production:")
        for name in COMPONENTS:
            if name not in desired.get("production", {}):
                continue
            out.append(f"    {name}:")
            for field in DESIRED_FIELDS:
                out.append(f"      {field}: {_emit_scalar(str(desired['production'][name][field]))}")
    if record.get("yuelink"):
        out.append("yuelink:")
        for field in YUELINK_FIELDS:
            out.append(f"  {field}: {_emit_scalar(str(record['yuelink'][field]))}")
    return "\n".join(out) + "\n"

def validate(record: dict) -> list[str]:
    problems: list[str] = []
    schema = str(record.get("schema", ""))
    if schema not in READABLE_SCHEMAS:
        problems.append(f"schema 必须是 {' / '.join(READABLE_SCHEMAS)}，读到 {record.get('schema')!r}")
    comps = record.get("components")
    if not isinstance(comps, dict) or not comps:
        problems.append("components 缺失或为空")
        comps = {}
    for name, body in comps.items():
        if name not in COMPONENTS:
            problems.append(f"未知组件 {name!r}（合法：{', '.join(COMPONENTS)}）")
            continue
        if not isinstance(body, dict):
            problems.append(f"{name}: 不是映射")
            continue
        for field in FIELDS:
            if field not in body:
                problems.append(f"{name}: 缺字段 {field}")
        for field in body:
            if field not in FIELDS:
                problems.append(f"{name}: 多出字段 {field}")
        rev, dig = body.get("revision", ""), body.get("digest", "")
        if not SHA_RE.match(str(rev)):
            problems.append(f"{name}: revision 不是 40 位十六进制：{rev!r}")
        if not DIGEST_RE.match(str(dig)):
            problems.append(f"{name}: digest 不是 sha256:<64-hex>：{dig!r}")
        if not TS_RE.match(str(body.get("promoted_at", ""))):
            problems.append(f"{name}: promoted_at 不是 UTC 秒级 ISO-8601（Z 结尾）：{body.get('promoted_at')!r}")
        if not RUN_ID_RE.match(str(body.get("run_id", ""))):
            problems.append(f"{name}: run_id 不是数字或 unknown：{body.get('run_id')!r}")
        by = str(body.get("promoted_by", ""))
        if not by.strip() or "\n" in by:
            problems.append(f"{name}: promoted_by 为空")
    yl = record.get("yuelink")
    if yl is not None:
        if not isinstance(yl, dict):
            problems.append("yuelink: 不是映射")
        else:
            for field in YUELINK_FIELDS:
                if field not in yl:
                    problems.append(f"yuelink: 缺字段 {field}")
            for field in yl:
                if field not in YUELINK_FIELDS:
                    problems.append(f"yuelink: 多出字段 {field}")
            if not VERSION_RE.match(str(yl.get("version", ""))):
                problems.append(f"yuelink: version 形状不对：{yl.get('version')!r}")
            if not SHA_RE.match(str(yl.get("source_commit", ""))):
                problems.append("yuelink: source_commit 不是 40 位十六进制")
            if not HEX64_RE.match(str(yl.get("update_manifest_sha256", ""))):
                problems.append("yuelink: update_manifest_sha256 不是 64 位十六进制")
    # yueops 三镜像同 revision 不再是形状规则（P2 §5.2 B1）：跨 revision 必须输入等价，
    # 那需要 git 与指纹实现，由 group_consistency() 在 write / verify / source-check 里判。
    problems.extend(_validate_desired(record, schema, comps))
    for key in record:
        if key not in ("schema", "components", "desired", "yuelink"):
            problems.append(f"顶层多出键 {key!r}")
    return problems


def _validate_desired(record: dict, schema: str, comps: dict) -> list[str]:
    """schema 1 不许有 desired；schema 2 必须有，且覆盖恰好 components 里的组件集合。
    A3 起 desired 的值可以与 components 不同（--rollback 显式回退），但形状必须合法。"""
    desired = record.get("desired")
    if schema == "1":
        return ["schema 1 不许带 desired（desired 从 schema 2 起）"] if desired is not None else []
    if schema != "2":
        return []
    if not isinstance(desired, dict):
        return ["schema 2 缺 desired 段"]
    problems: list[str] = []
    for key in desired:
        if key not in ("generation", "production"):
            problems.append(f"desired: 多出字段 {key}")
    if not GENERATION_RE.match(str(desired.get("generation", ""))):
        problems.append(f"desired.generation 不是正整数：{desired.get('generation')!r}")
    production = desired.get("production")
    if not isinstance(production, dict):
        return problems + ["desired.production 缺失或不是映射"]
    if set(production) != set(comps):
        problems.append(f"desired.production 的组件集合 {sorted(production)} 不等于 components 的 {sorted(comps)}"
                        "（desired 必须覆盖每一个已 promote 的组件）")
    for name, body in production.items():
        if name not in COMPONENTS:
            problems.append(f"desired.production: 未知组件 {name!r}")
            continue
        if not isinstance(body, dict) or set(body) != set(DESIRED_FIELDS):
            problems.append(f"desired.production.{name}: 字段必须恰好是 {', '.join(DESIRED_FIELDS)}")
            continue
        if not SHA_RE.match(str(body["revision"])):
            problems.append(f"desired.production.{name}.revision 不是 40 位十六进制：{body['revision']!r}")
        if not DIGEST_RE.match(str(body["digest"])):
            problems.append(f"desired.production.{name}.digest 不是 sha256:<64-hex>：{body['digest']!r}")
    return problems

def signature_path(path: Path = RELEASE_YAML) -> Path:
    return path.with_name(path.name + SIGNATURE_SUFFIX)


def verify_signature_bytes(data: bytes, signature: bytes) -> tuple[str, str]:
    """(status, detail)；status ∈ unsigned / unverifiable / invalid / verified。"""
    if not signature:
        return "unsigned", "签名字节为空"
    gpgv = shutil.which("gpgv")
    if gpgv is None:
        return "unverifiable", "gpgv 没装"
    if not SIGNER_KEYRING.is_file():
        return "unverifiable", f"钥匙环 {SIGNER_KEYRING} 不在（yueops 未检出？）"
    with tempfile.TemporaryDirectory(prefix="release-yaml-verify.") as work:
        body, sig = Path(work) / "release.yaml", Path(work) / "release.yaml.asc"
        body.write_bytes(data)
        sig.write_bytes(signature)
        proc = subprocess.run([gpgv, "--homedir", work, "--keyring", str(SIGNER_KEYRING.resolve()),
                               "--status-fd", "1", str(sig), str(body)],
                              capture_output=True, text=True, timeout=30, check=False)
    valid = [line.split() for line in proc.stdout.splitlines() if line.startswith("[GNUPG:] VALIDSIG ")]
    if proc.returncode == 0 and len(valid) == 1 and valid[0][2] == PINNED_SIGNER and valid[0][-1] == PINNED_PRIMARY:
        return "verified", f"由 {PINNED_SIGNER}（主钥 {PINNED_PRIMARY}）签出"
    seen = ",".join(v[2] for v in valid) or "无"
    return "invalid", f"gpgv rc={proc.returncode}，VALIDSIG={seen}，钉住的是 {PINNED_SIGNER}"


def verify_signature_file(path: Path = RELEASE_YAML) -> tuple[str, str]:
    """(status, detail)；status ∈ unsigned / unverifiable / invalid / verified。
    与 yueops 消费端同一判据：gpgv + 固定钥匙环，VALIDSIG 恰好一条、子钥与主钥指纹都等于钉住的值。"""
    sig = signature_path(path)
    if not sig.is_file():
        return "unsigned", f"{sig} 不存在"
    try:
        return verify_signature_bytes(path.read_bytes(), sig.read_bytes())
    except OSError as exc:
        return "unverifiable", str(exc)
