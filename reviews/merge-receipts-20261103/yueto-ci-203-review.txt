# Evidence discipline (Yue.to)

For post-release readback, read-only accounting reconciliation or routine
inspection, read [Read-only operational evidence](references/readonly-operations.md).
It supplies collection criteria without authorizing production access or repairs.

The most common failure here is a conclusion with **no supporting evidence**
whose output looks identical to an evidenced conclusion. On 2026-08-29 this
recurred independently in five unrelated places, including two newly written
scripts.

Every rule below comes from an observed incident. Use `guard-authoring` to write
guards and `fleet-diagnose` to investigate nodes. This skill governs **the claim
you are about to make**.

## Select the evidence before collecting again

Start with the selected item's latest receipt: object/input revision, environment
(including timezone, shard order and concurrency when relevant), covered behavior,
result, timestamp and evidence path. Reuse matching evidence within 24 hours;
remeasure changed inputs, conflicting results or expired evidence. A changed
runtime/environment changes the object even if the source SHA is unchanged.
Collect only the missing obligation. A targeted test proves that tested behavior;
it does not replace a required full release gate or current production readback.
State the claim at the layer actually observed and close the item once its
acceptance is satisfied. Historical incidents without a denominator establish
failure mechanisms, not an error rate or a measured performance improvement.

## Answer three questions before stating a conclusion

1. **What does this output say when probing fails?** If it looks the same as
   health or failure, it has no evidentiary value.
2. **Did I observe not-X, or merely fail to observe X?** These are different
   propositions.
3. **Did I measure the layer I am making a claim about?** Inbound reachability
   is not usability, ICMP is not the data plane, and cached receipts are not
   liveness.

If any answer is missing, report **UNKNOWN / UNMEASURABLE**, not either verdict.

## 1. Unmeasurable state mistaken for a definite verdict

This causes both **false green** (unreachable becomes healthy) and **false red**
(unreachable becomes failed). Observed forms include:

- SSH fails, collection returns an empty string, and output says HY2 is not
  listening on UDP/443. That is a data-plane claim supported only by inability
  to reach the host.
- An observation point outside China judges whether the Chinese path is blocked.
  That plane cannot observe the proposition, always returns UP and vetoed
  recovery for 9 hours. **Write down what a veto gate can establish first.**
- `dev-null-fleet-guard` reports SEEN from a cached `checked_at` receipt; it does
  not establish liveness.
- A listener assertion after `sleep 15` mistakes a host taking longer than
  15 seconds to bind for a host unable to start. **Poll readiness until it appears**
  within the operation's bound instead of assuming a fixed wait suffices.
- All inbound 443 checks pass while outbound access reaches only the same
  datacenter (`yue-us-premium`). Reachability does not establish usability.

Fallback repair can hide this family completely: "fails every time and gets
repaired" and "never failed" can produce identical observable state. A timer
that repairs the state every N minutes is itself a reason to inspect the path.
Where authorized and operationally appropriate, suspend the fallback for the
measurement so it cannot mask the failure; preserve the recovery path.

For every collect-then-assert path, first prove collection succeeded (nonempty,
expected fields), then inspect contents. Missing measurements are
UNKNOWN/UNREACHABLE. An inspection unable to measure should `exit 75`, not
`exit 1`.

## 2. A negative observation requires proof of handler arrival

A rate-limit test sent 30 fake tokens to `checkin.yue.to/api/client/feedback`
and counted 30 non-429 responses as passes. That hostname actually returned
404: thirty 404s had been mistaken for thirty admitted requests.

"No rate limit/error/alert" and "code was never reached" have identical counts.
Anti-probing decoy 404s can further hide a missing route as bad data.

First obtain a signal **generated by the target handler itself**, such as an
empty-body 400 `content_required`, not a 404 from elsewhere. Then count results.
Run a negative/control comparison too: a blocking result may have blocked
legitimate traffic as well.

## 3. The tool can manufacture evidence

Every example below has contaminated actual conclusions:

| Failure shape | Consequence | Check or remedy |
|---|---|---|
| Read `$?` after `cmd \| tail` | Captures tail's status; four mutation runs falsely passed | Capture `rc=$?` immediately on its own line, with no intervening command, including `echo`; preserve the producer status |
| `echo "rc=$?"` also contains `$(date)` | Command-substitution expansion overwrote status; rc 78 was recorded as 0 | Capture status separately and immediately |
| `ssh -n` with heredoc/`bash -s` | stdin becomes /dev/null; remote reads zero bytes and always exits 0 | Look for `-n` and `<<` together |
| `${...}`/backticks in a remote SSH command | Premature remote-shell expansion produced two opposite fleet conclusions in one day | Include a known-good control host in the same batch |
| zsh `$VAR:path` | Modifier parsing silently rewrites the command; errors name a nonexistent file | Quote the whole value |
| `__pycache__` / Flutter kernel cache | Same-length edits loaded stale bytecode; all four mutations falsely passed | After editing, `sleep 2 && touch`, or clear the relevant cache |
| Playwright `fullPage` stitching | Turned an entire home section white; visual baseline missed three major regions | Quantify pixels rather than trusting visual inspection alone |
| Matching structural fingerprints | Reported green for syntactically invalid YAML | Require successful parsing; shape alone is insufficient |
| Background jobs inherit `SIGINT=SIG_IGN` | Bash cannot install a trap for an already ignored signal | A failure only in the SIGINT parameter is the signature |

## 4. The criterion itself can be wrong

- **Too broad:** `dpkg -l | awk '$1 !~ /^ii/'` treated normal `rc` (removed,
  configuration retained) as failure and reported every host failed after a
  successful rollout. The intended predicate is `^i[^i]`.
- **Too narrow/non-universal:** `ss | grep -c :443` is 2 on a dual-stack host,
  not 1. Establish universality before asserting an exact count.
- **Measuring the probe:** instantaneous single samples, counting the probe
  itself, or self-matching `pgrep -f X`.
- **Wrong method:** binary-search MTU on a lossy path mistakes loss for oversized
  packets. Repeat fixed-size probes and inspect the pattern, not the converged
  search value.
- **Agreement is not correctness:** comparing two handwritten copies detects
  one-sided changes but is blind when both are stale. All four checks passed
  during actual Thailand2/Indonesia2 VLESS disconnections. Ask who detects A
  and B being wrong together; add a runtime-derived observation when necessary.
- **Contaminated sampling:** check for other heavy work in the sample window
  before attributing load. Geodata distribution once caused 5 false positives.
- **Inventory is not forwarding topology (2026-10-08):** do not combine
  `servers/server_nodes` hosts, protocol nodes, relay membership and other
  product pools. Distinguish entry SID, logical node ID and actual backend.
  Read current nginx upstreams, HY2 MAP and loaded nft targets, then reconcile
  native machine presence. One node ID bound to several hosts proves bindings
  only, not multiple current v4 exits in a region or readiness for backend load
  balancing. Measure primary/backup entry and exit redundancy separately.
- **Batch success is not item success (2026-10-08):** a protocol sweep using
  consecutive-failure alerting can `exit 0` with VLESS 49/50. Locate the exact
  invocation output with
  `systemctl show <unit> -p InvocationID -p Result -p ExecMainStatus -p StandardOutput`,
  then verify each protocol's denominator and OK/FAIL/UNKNOWN counts. A later
  96/96 cannot erase the prior failure. Handshake reachability is not bandwidth
  recovery evidence.
- **Queued alerts are not delivered alerts (2026-10-08):** P1 deferred ACK proves
  durable acceptance only. Use the original event's dedupe key/source generation
  to correlate `ops_alert_outbox`, the actual batch's `delivered_at` and native
  send ACK; compare payload hash and timing. Before an hourly batch is due,
  report queued. Missing delivery links mean UNKNOWN. Extra test messages cannot
  substitute for evidence of the original alert chain.

## 5. The source itself can be stale

- IPs taken from old rollout logs make healthy hosts appear unreachable. Verify
  the current address before a liveness verdict.
- Cross-repository assertions in comments expire unnoticed; one guided
  production for three months.
- Backlogs age: when asked what remained in `endgame-plan`, 4 items were already
  complete and 1 was hidden in a merged row. Reconcile before working.
- Of 15 self-reported visual defects, 6 were observation errors. Measure before
  changing code.
- A benchmark site with fabricated data entered long-term memory and was cited
  as measured evidence for 9 days.

## Pre-conclusion checklist

- [ ] Probe failure is distinguishable from the claimed verdict.
- [ ] Negative results have independent arrival proof and controls.
- [ ] Fleet-wide claims include a known-good host in the same batch.
- [ ] Numbers come from current authoritative sources, not old logs/comments/lists.
- [ ] Measurement and claim concern the same layer.
- [ ] Repair timers cannot silently mask the behavior being measured.
- [ ] Report inability to measure explicitly; it is a valid, necessary conclusion.

# Verification Before Completion

## Overview

**Core principle:** Evidence before claims, always.

**Violating the letter of this rule is violating the spirit of this rule.**

## The Iron Law

```
NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE
```

If you haven't run the verification command in this message, you cannot claim it passes.

## The Gate Function

```
BEFORE claiming any status or expressing satisfaction:

1. IDENTIFY: What command proves this claim?
2. RUN: Execute the FULL command (fresh, complete)
3. READ: Full output, check exit code, count failures
4. VERIFY: Does output confirm the claim?
   - If NO: State actual status with evidence
   - If YES: State claim WITH evidence
5. ONLY THEN: Make the claim

Skip any step = lying, not verifying
```

## Common Failures

| Claim | Requires | Not Sufficient |
|-------|----------|----------------|
| Tests pass | Test command output: 0 failures | Previous run, "should pass" |
| Linter clean | Linter output: 0 errors | Partial check, extrapolation |
| Build succeeds | Build command: exit 0 | Linter passing, logs look good |
| Bug fixed | Test original symptom: passes | Code changed, assumed fixed |
| Regression test works | Red-green cycle verified | Test passes once |
| Agent completed | VCS diff shows changes | Agent reports "success" |
| Requirements met | Line-by-line checklist | Tests passing |

## Red Flags - STOP

- Using "should", "probably", "seems to"
- Expressing satisfaction before verification ("Great!", "Perfect!", "Done!", etc.)
- About to commit/push/PR without verification
- Trusting agent success reports
- Relying on partial verification
- Thinking "just this once"
- Tired and wanting work over
- **ANY wording implying success without having run verification**

## Rationalization Prevention

| Excuse | Reality |
|--------|---------|
| "Should work now" | RUN the verification |
| "I'm confident" | Confidence ≠ evidence |
| "Just this once" | No exceptions |
| "Linter passed" | Linter ≠ compiler |
| "Agent said success" | Verify independently |
| "I'm tired" | Exhaustion ≠ excuse |
| "Partial check is enough" | Partial proves nothing |
| "Different words so rule doesn't apply" | Spirit over letter |

## Key Patterns

**Tests:**
```
✅ [Run test command] [See: 34/34 pass] "All tests pass"
❌ "Should pass now" / "Looks correct"
```

**Regression tests (TDD Red-Green):**
```
✅ Write → Run (pass) → Revert fix → Run (MUST FAIL) → Restore → Run (pass)
❌ "I've written a regression test" (without red-green verification)
```

**Build:**
```
✅ [Run build] [See: exit 0] "Build passes"
❌ "Linter passed" (linter doesn't check compilation)
```

**Requirements:**
```
✅ Re-read plan → Create checklist → Verify each → Report gaps or completion
❌ "Tests pass, phase complete"
```

**Agent delegation:**
```
✅ Agent reports success → Check VCS diff → Verify changes → Report actual state
❌ Trust agent report
```

## When To Apply

**ALWAYS before:**
- ANY variation of success/completion claims
- ANY expression of satisfaction
- ANY positive statement about work state
- Committing, PR creation, task completion
- Moving to next task
- Delegating to agents

**Rule applies to:**
- Exact phrases
- Paraphrases and synonyms
- Implications of success
- ANY communication suggesting completion/correctness

## Cross-repo coupling that isn't visible in any single repo

- **Subscription generation is a contract between yueboard and every client family.** `yueboard/internal/modules/subscribe/` renders Clash Meta, Surge, Loon, Quantumult X, Surfboard, sing-box, and general links from native templates. There is no `?yl=1` or device-specific server branch. When one client fails, render its exact User-Agent and compare fields against a working renderer before changing the fleet.
- **The server template is the YueLink source of truth.** YueLink no longer inlines `GeoIP.dat`/`GeoSite.dat`; it seeds the exact bundled `.mrs` set and preserves server routing. Keep client transforms bounded to compatibility defaults, and use the reference clients to justify any divergence.
- **The schema is native; remaining cross-service reads are explicit migration debt.** Tables use native names, `numeric` amounts, `jsonb`, and `timestamptz`. YueBoard owns panel-domain writes. Any temporary YueOps read must be catalogued and moved behind a scoped native internal API before its DB credential is removed.
- **Panel↔node control is ConnectRPC only.** The protobuf contract is shared by yueboard and yue-node. Every physical host must use a machine-scoped credential and exact assignment; a fleet-wide token, REST polling, or WS push is a migration regression.
- **🚨 Never rebuild a node by copying another node's `/home/yue-node` wholesale.** The runtime tree
  contains `node-*/data/report-outbox`, which is the machine's **billing identity**. Cloning it either
  double-bills or wedges the node forever on `report sequence gap`, which has no recovery path. This
  has now happened twice (2026-08-01, 2026-08-11). **Wipe `node-*/data/report-outbox` before first
  start** — the in-code owner guard only protects hosts already running yue-node `4bf9ada` or newer.
  📎 Full provisioning / cloning / retiring / hard-delete procedure: the **`node-lifecycle`** skill.

## Release / CI: what is true in every session

Four things must name the same commit: the reviewed **pin**, the source repo **HEAD**, the
**promoted** image, and what **production** actually runs. `release-state.py` prints all four.
- **2026-10-12: SSH authority is ACTIVE.** Every new yueops revision needs auto-pull + `make-release-root.sh
  --strict` + `scripts/ship-sshd-authority.py --apply` before Ops/panel deploys or A/B publishing (ship.sh chains them).
- **2026-10-11: bastion is CPU-steal-bound** (60–78%): no heavy tests there; check `vmstat` st first. 📎 `release-chain`.

**Before pushing `yueboard/master`, establish its effect on the active release.**
Promotion requires default-branch ancestry, inputs identical to HEAD and a candidate
not older than `:latest`. A changed input can invalidate a running release.
When inputs change, the integration owner must complete these steps:

1. Read the revision labels off the **running production** panel image and node fleet, then run
   `scripts/converge-yueboard-release-pin.py --from-head --deployed-board-revision <prod-board>
   --deployed-node-revision <prod-node>`. Both are explicit because reviewed candidates may never
   have been deployed. It updates yueto-ci's two copies atomically and **derives** the schema
   floor from `git show <rev>:schema-floor.txt`; since P2 §4 A3 it no longer writes yueops.
2. Coordinate the required rebuild and panel deployment with the release owner.
   The desired state yueops deploys from is the **signed** root `release.yaml`
   (ship.sh writes + seals it; no pin is committed back into yueops). 📎 `release-chain`.

Promote, `release-state.py` and the schema-migrator contract accept a descendant
with unchanged native image inputs and the same schema floor while retaining the
reviewed pin. Use the actual input comparator: a Markdown or test filename alone
does not establish equivalence. Changed or unknown inputs retain the normal pin
convergence and release requirements. Preserve each active writer's source custody.

🚨 **The private repos' Actions billing freeze comes and goes** — measure it (wall-clock + step count,

At release completion, the **reviewed pin, signed desired state, promoted image
and running production artifact** must identify the same release. Source HEAD
may be a successor with proven identical build inputs. Keep the image's actual
build revision; never relabel an older artifact as a new HEAD.

- Do not hand-edit pins. The authorized writer is
  `scripts/converge-yueboard-release-pin.py --from-head --deployed-board-revision <production-board> --deployed-node-revision <production-fleet>`.
  It updates the copies atomically and derives the schema floor from
  `git show <rev>:schema-floor.txt`; the floor is not an input.
- The two `--deployed-*` revisions validate ancestry only: deployed Board must
  precede the candidate, and deployed Node must precede the sidecar candidate.
  They are no longer recorded in files. The Release-A predecessor/target contract

  pin convergence only.

  three former projections caused a Board-to-Ops release cycle. Commit yueto-ci
  after convergence; promotion reads that reviewed state.
- Do not hand-edit `release.yaml`. `ship.sh` writes it and `release-yaml.py seal`
  signs it. YueOps deployers, rollouts and migrators consume only verified signed
  state. Deliberate rollback uses `release-yaml.py write --rollback` then `seal`;
  late older candidates cannot overwrite newer desired state.

  `.gitleaksignore` to lead the pin. Use the existing fingerprints in

  inputs since 2026-09-30. Advancing it alone does not move the reviewed pin,

  remain build inputs and require a reviewed release when changed.
- For a new candidate, converge the reviewed pin first, then run
  `release-yaml.py source-check` for ancestry and floor. Do not declare release
  consistency before promotion and production readback.
