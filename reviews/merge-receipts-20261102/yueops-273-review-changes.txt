### Two-stage rollout for check-in traffic settlement

The panel_ledger ACK consumer reads the original byte-allocation plan in reward-anchor `metadata.traffic_settlement_v1`. It validates subject, reference, idempotency key and actual receipt range, then updates every row and marks the outbox done in one transaction. Invalid plans must not fall back to single-row allocation. The plan is server-only, excluded from Board wire and user responses; existing single-row semantics for other producers stay unchanged.

Release consumer-only first, keeping the old check-in producer. Read back the images for checkin-api's resident worker and yue-bot's watch consumer, including exit of the old processes, before releasing the producer. Native service order is web → checkin → bot; **do not skip the intermediate consumer-only release**. Producer rollback must target consumer-only. While new-format work is unfinished, do not downgrade to an old consumer that cannot process it.

The producer creates all reward rows in one transaction, then links `outbox.reward_ledger_id` to the first traffic row. Plan-request bytes and Board payload use the same integer. Four-decimal GB amounts use differences between cumulative actual values; `metadata.applied_bytes` retains exact bytes.

### Auth API

- **Two-factor login is mandatory (2026-09-26).** Primary entry: YueBoard admin's YueOps console item → `/sso/board` → `POST /auth/board-sso`; Board TOTP/passkey supplies the second factor. Public `POST /auth/login` password validation is only the first factor and returns `{second_factor_required:true, second_factor:"board_sso"}`, **without issuing a session**. Accounts without `board_user_id` return403 `second_factor_unavailable`. Bastion loopback with no `CF-Connecting-IP` is the password-only emergency entry, returning `{access_token, must_change_password}`. `POST /auth/change-password` accepts `{old_password,new_password}` (≥8 characters).
- WS `/api/tasks/{id}/ws` accepts the token only in `Sec-WebSocket-Protocol`, never the query string.
- Trust X-Forwarded-For only when `request.client.host` is127.0.0.1 or`::1`.

# yueops-agent-deploy

### 宿主 agent（`scripts/agent.sh`）—— 动它之前必读

- **分发是 push，不是 pull**：唯一事实源是本仓 `scripts/agent.sh`；它被 baked 进 yueops-web 镜像（Dockerfile 的运行时子集 COPY，清单 `services/yueops-web/runtime-scripts.json`，P2 C3）并随 pinned checkout 落在 bastion `/opt/yueops/scripts/`，再由 `deploy.py upload_scripts()` **scp 到节点** `/home/yue-node/agent.sh`。节点侧没有任何自更新，`/api/metrics/agent/agent.sh` 只在一键安装时被拉一次（**注意带 `/metrics`**：该路由挂在 `APIRouter(prefix="/metrics")` 上、再被 app 以 `/api` 前缀挂载。本文此前与 `web/api/metrics.py` 的安装模板一起写成 `/api/agent/agent.sh`，2026-08-17 实测 404，而模板 `set -euo pipefail` 会让一键安装当场中止；两处已同时更正）。⚠️ 就地覆盖必须 `mv` 原子替换：bash 是按 fd 增量读脚本的，truncate-rewrite 会打乱正在跑的进程。
- **🚨 配置只在启动时读一次 → 加固过的解析器可以潜伏数周**。agent.sh 要求 `.agent.env` 是 owner-only 常规文件且 `AGENT_TOKEN` 匹配 `^[A-Za-z0-9_-]{32,256}$`，不满足就打一行日志 `exit 1`。2026-08-02 实测：全队 39/39 的 `.agent.env` 是 0644、token 是 26 字符的 `yueops-agent-default-token`，**盘上的 agent.sh 从来没成功跑起来过**——跑着的都是加固前载入的旧副本，每台机离「一次 restart 即静默失联」只差一步。单测/部署测试都看不见这个状态，守卫是 `audit-agent-runtime-config.timer`（尤其那条「在跑的进程比盘上的脚本还老」）。
- **`agent_token` 是单值共享凭据，轮换必然是 flag day**：`_verify_agent` 只比对一个值，没有 dual-accept。2026-08-02 轮换成 48 hex 的可行顺序 =「① 把新 `.agent.env`+新 agent.sh 铺满全队但**不重启**（在跑的 agent 把旧 token 揣在内存里，照常上报，零影响）→ ② 改 DB `settings.agent_token` → ③ `docker restart yueops-web` 清掉 300s token 缓存 → ④ 分批 `systemctl restart yueops-agent`」。②→④ 之间该机 metrics 403，实测全队空窗 ~4.5 分钟；`direct-node-liveness.timer` 的 `STALE_MIN=10` 是硬约束，超时会 39 台一起告警，所以要么压在 10 分钟内、要么先 stop 该 timer 再恢复。
- **这个 token 不是「只影响仪表盘」**：`POST /api/metrics/{sid}` 里带着动态 IP 检测，能改写 `servers.ip` 并触发 DNS + 面板 host 更新。伪造上报 = 改 DNS。
- **🚨 别按 `servers.ip` 拨 SSH**：14 台 direct 的 `servers.ip` 是 IPv6 字面量，bastion 对它们 ICMP6 通、TCP 22 一律超时（历史结论「bastion 没有 v6 出口」是错的）。它们的 `servers.domain` **有 A 记录且 SSH 正常**。此前 `audit-node-instance-identity.sh` 把这 14 台一律记 SKIP——那条专门抓计费被丢弃的审计在三分之一舰队上结构性失明。统一走 `scripts/lib/fleet-ssh-address.sh` 的 `yueops_fleet_ssh_addr`（先试库存 IP，再退域名 A 记录；主机密钥仍钉在 `HostKeyAlias=<sid>`，换地址不换信任）。
- **maintenance 机器的库存 IP 会冻结**：`report_metric` 在 `deploy_mode == maintenance` 时提前 return，动态 IP 检测根本不执行，所以 `servers.ip` 会停在进入维护那一刻。2026-08-01 的 `yue-tw` 隔离曾触发这一形态；该机现已重新验收为 direct，不是当前 maintenance。隔离期间找实时地址可查 `docker logs yueops-web | grep 'POST /api/metrics/<sid>'` 的源 IP 审计行。
- **`report_machine_status` 与 metrics 上报互不影响**（`report_machine_status "$payload" || true`，且用逐机 machine-scoped 凭据打 yueboard ConnectRPC）。所以 metrics 403 不会波及面板侧机器存活；反过来 agent 进程死了两条一起停。

### deploy_mode

> 2026-08-19 仓库目标为 44 direct + 2 relay、maintenance=1；目标 maintenance 行是
> 整机死亡后保留事故证据的 `yue-tw-3`。同日生产只读 inventory 仍为 45 direct；

> 2026-08-01 隔离事故教训，不能覆盖上述当前证据边界。

- **`direct`** — 承载 hy2 + vless-reality 的落地主机，有 agent；这只是部署类型，不等于客户端入口直连。用户入口矩阵：AI、家宽、专属、普通香港/台湾直连；其他普通节点（含 VN79/81）固定走 canonical `v4.yuetoto.net`。

# Guard authoring (Yue.to)

The expensive failure is a green guard protecting nothing. The linked incident examples
occurred in actual production work.

Apply the checklist to the guard's actual inputs, dependencies and claimed
coverage. Running an existing check does not require redesigning it. A changed
assertion, scan boundary or success/failure classification does require this skill.
For import/fixture leakage, load [test isolation](references/test-isolation.md)
first; use the guard checklist only if guard coverage changes.

Before adding an invariant, establish which consumer needs it and check its
actual semantics. Challenge it with one realistic counterexample at that boundary:
subprocess execution for locks, a write failure for persistence, or raw single-target
output for collectors. Matching strings or unrelated runner-image labels cannot
establish those properties. Reuse the recorded interpreter/image, user and mounts;
classify failures as startup, collection or assertion before editing product code.

## Establish three facts before accepting green

1. Did this run reach the target? Zero executions is not a pass.
2. Did the scan cover the intended objects? Zero matches is not universal success.
3. Is the guarded layer the layer users and production actually encounter?

A negative answer makes the green result meaningless.

# Prove that a guard detects a real failure

Before delivery, establish all three properties:

1. **It fails when the protected fact is broken.** Run a mutation test; without
   this, the guard is not delivered.
2. **It checks the actual consumer.** Importability does not establish execution.
   Removing `if __name__ == "__main__"` can leave importlib-based tests green
   while the actual script silently exits without doing work.

are not discovered by pytest's default patterns.

#

OUTBOX_RETRY_ATTEMPTS=${OUTBOX_RETRY_ATTEMPTS:-5}

run_async() {
    local line="$1" attempt rc
    IFS='|' read -r sid host mode user port <<< "$line"
    for attempt in $(seq 1 "$OUTBOX_RETRY_ATTEMPTS"); do
        # rc 必须在 else 分支里取:`if cmd; then ...; fi` 之后的 $? 是整个 if
        # 复合命令的状态(条件为假且无 else 时是 0),不是 cmd 的退出码。
        if rollout_one "$sid" "$host" "$user" "$port" "$mode"; then
            echo "  OK $sid" | tee -a "$RUN_LOG"
            return 0
        else
            rc=$?
        fi
        if [ "$rc" -eq 44 ]; then
            # 没连上 ≠ 滚动失败。这台机器没被碰过，继续调度后面的主机不会扩大
            # 爆炸半径。但它**绝不能**被算成 OK：不可达是 UNKNOWN，
            # 与健康主机长得一样正是最贵的那类误判。
            echo "  UNREACHABLE $sid" | tee -a "$RUN_LOG"
            return 44
        fi
        if [ "$rc" -ne 42 ]; then
            break
        fi
        [ "$attempt" -lt "$OUTBOX_RETRY_ATTEMPTS" ] || break
        echo "  RETRY $sid (accounting report in flight, attempt $attempt)" |
            tee -a "$RUN_LOG"
        sleep "$OUTBOX_RETRY_DELAY"
    done
    echo "  FAIL $sid" | tee -a "$RUN_LOG"
    return 1
}

# Begin pure node-rollout per-node failure policy (kept independently executable in tests).
# Owner decision 2026-11-02 20:05 SGT: after the canary ring passed, one node
# that fails to deploy (e.g. prepare exit 52) is marked FAILED and skipped; the
# remaining waves continue. One node must never stall the fleet. Failed nodes
# are listed in the final summary/alert and redeployed one by one with
# scripts/redeploy-yue-node.sh. A fleet-wide failure ratio above
# ROLLOUT_MAX_FAIL_PERCENT (default 20) still stops scheduling: that pattern is
# systemic, not one bad host. The canary gate above is unchanged.
fleet_failure_ratio_exceeded() {
    # $1 failures so far, $2 fleet (non-canary) hosts targeted by this run.
    local failures=$1 target=$2 pct=${ROLLOUT_MAX_FAIL_PERCENT:-20}
    [ "$target" -gt 0 ] || target=1
    [ $((failures * 100)) -gt $((pct * target)) ]
}
