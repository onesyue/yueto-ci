# Complete Ops PR admission and evidence

`ops-pr-validation.yml` is a validation-only reusable workflow. It derives the canonical `build.yml` Ops worker and join through `scripts/generate-pr-validation.py`; it does not build, promote, publish, deploy, or request write permissions. The runtime policy is pinned by `pr-validation-policy.json`. The drift test requires both the generated job graph and the frozen policy inputs to match the canonical ship implementation. Update the reviewed policy pin and regenerate when those inputs change.

A trusted fetch job checks the actual same-repository pull-request event, fetches the exact head and pinned Board Git objects, and uploads bundles to the **private caller run**. Only this job receives `YUEBOARD_SOURCE_READ_TOKEN`. It must be a dedicated identity with contents:read and metadata:read access to `onesyue/yueboard`, not a publishing PAT, SSH secret, or App private key. Candidate tests run on separate allocations with no such credential. Git bundles contain objects, not checkout credential configuration. Fork requests fail closed.

The PR boundary requires enrolled, signed source evidence and refuses the legacy-baseline fallback. The planner, every selected role, PostgreSQL toolchain, native obligations and final join use the existing canonical implementation. The actual Ops caller repository, merge/event SHA, head SHA, run ID and attempt remain distinct from the central policy revision; they are never rewritten to impersonate a public run. Migration checking uses the event's exact base SHA and verifies it is an ancestor of the head. All selected jobs must succeed; failed, missing, cancelled or skipped joins cannot produce the stable `Ops admission and evidence` success.

The Ops caller should have no path filters and use `pull_request` (opened, synchronize, reopened, ready_for_review). Its only job calls `onesyue/yueto-ci/.github/workflows/ops-pr-validation.yml@<reviewed full commit SHA>`, with `permissions: contents: read` and the explicitly named Board read credential. Do not use `secrets: inherit`, `pull_request_target` candidate execution, arbitrary policy/role inputs or dispatch credentials. Pin the reusable workflow to the reviewed final commit; its own fixed policy dependency is recorded separately.

## Configuration and deployment status

The read-only repository check on 2026-11-12 returned `onesyue/yueops` Actions `enabled: false`. Repository-level secret metadata also did not establish a dedicated Board source-read credential. Consequently, no actual Ops PR full-matrix run or negative PR run is claimed. This change does not enable Actions, create secrets, configure rulesets, dispatch runs, or claim the check is currently required. Those are separate authorized configuration actions. Reusable-workflow runtime and billing belong to the private caller, not the public YAML repository.

After configuration is separately authorized, validate the natural PR run at its exact head with all role artifacts and `VALIDATION_MATRIX_COMPLETE`, plus a negative PR that fails admission. Required-check/ruleset configuration must bind the reviewed workflow origin; a same-named candidate-controlled job is not an equivalent trust boundary. Existing admission-precheck remains a fast check, not a substitute for this full gate.
